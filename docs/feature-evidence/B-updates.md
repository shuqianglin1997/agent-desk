# B - Per-account app updates: research report

## Part 1 - Repo (line numbers approximate to a few lines where marked ~)
- src/tool-maintenance.js:4-6 says the module "deliberately does not execute updates"; it only builds plans. Desktop catalog entries (claude, codex, cursor, kimi) at :24-56 have only `appIds` and `officialUrl`. `updatePlanFor` (:459-463): any desktop record gets `{mode:'manual', reason:'desktop-managed'}`. CLI plans: npm / brew / uv / standalone self-update (`selfUpdateArgs`, e.g. `claude update`) (:465-498); `updateArgumentsFor` (:500-515) turns a plan into argv (`npm install --global pkg@latest`, `brew upgrade`, `uv tool upgrade`).
- The executor is src/main.js: `tools:scan/open/update` handlers (:482-490), `maintenanceCommand` (:4852), `updateMaintenanceTool` (:4866-4915; ~:4870 a desktop/manual plan just calls `openMaintenanceOfficialPage`, :4712, which opens the vendor download page with `shell.openExternal`), `runMaintenanceCommand` (:4917-4975, spawn, 'ignore' stdin, timeout, output tail). Desktop apps are therefore never updated by AgentDesk, and nothing checks whether profiles are running before a CLI update.
- Version discovery for desktop apps: `desktopBundleVersion` (main.js:4402-4425) runs `plutil -extract CFBundleShortVersionString` on `<App>.app/Contents/Info.plist`; bundle id via `macBundleIdentifier` (:4137). App location: `findExecutable` over `launchers` with `bundleName`/`bundleIdentifiers` (apps.js:751-771; Codex also checks `com.openai.codex`, apps.js:293-306). Only the on-disk version is known, never the version a running process started from.
- Isolation and launch: Claude/Codex/Cursor/Kimi (non-Work) use `profileIsolation: chromium-user-data-dir` (apps.js:38-40, 124, 308, 373, 660); args = `--user-data-dir=<profilePath>` (apps.js:794-805). macOS launch uses `open -n -a` (src/mac-launch.js:29): many instances of ONE bundle. Kimi Work ignores the flag and is "official-default-only" (apps.js:447-449), so it cannot have per-account instances anyway.
- Runtime supervisor (src/profile-runtime.js): `clientProcessRecords(profile)` (:446-451) matches OS processes to a profile by user-data-dir path; `status(profile)` (:481-515) gives active / processCount / launchedAt / fuse; `terminateProcesses` (~:625-673) and `stopProfile` (:676-678), `stopAll` (:797) stop exactly one profile's processes. IPC: `profiles:launch` (main.js:1613), `profiles:runtimeStatus` (:1617), `profiles:stop` (:1623). Nothing records which app version a process started from, whether a conversation is running, or a "was open" list (records only persist launchPid/launchedAt/active/owned).

## Part 2 - How the clients update (primary sources)
**Electron / Squirrel.Mac.** Electron docs: macOS needs a signed app; `quitAndInstall` "closes all windows, then calls app.quit()"; downloaded updates also apply on next launch. Squirrel.Mac source (master; I read SQRLUpdater.m, ShipIt-main.m, SQRLInstaller.m, SQRLTerminationListener.m, SQRLShipItRequest.h, SQRLDirectoryManager.m, SQRLShipItLauncher.m):
- After download, `prepareUpdateForInstallation` (SQRLUpdater.m:1074-1093) writes ShipItState.plist (target = `currentApplication.bundleURL`, `bundleIdentifier`, `launchAfterInstallation:NO`) and starts the ShipIt launchd job right away. The job label and the cache dir (`~/Library/Caches/<bundle id>.ShipIt`, SQRLDirectoryManager.m:22,54) are per bundle id, not per process.
- ShipIt-main.m:92-123 `waitForTerminationIfNecessary` -> `SQRLTerminationListener(url, bundleIdentifier)`. SQRLTerminationListener.m: lists `runningApplicationsWithBundleIdentifier`, keeps those whose bundle URL equals the target, watches every PID, completes only when ALL have exited; no timeout; the list is read once (instances started later are not awaited, but SQRLInstaller.m:364-374 then fails with `AppStillRunning` and ShipIt retries, ShipIt-main.m:253).
- `relaunchToInstallUpdate` (SQRLUpdater.m:1096-1120) rewrites the state with `launchAfterInstallation:YES` and calls `[NSApp terminate]` on the requesting instance only. Other instances are not asked to quit. ShipIt waits for them; if they stay open, install is deferred and the requester stays closed.
- After installing, ShipIt launches `targetBundleURL` via NSWorkspace (ShipIt-main.m:177-245): one plain launch of the app, with NO `--user-data-dir`. Relaunch therefore lands in the default data dir, not the managed account.
- Local evidence (read-only): `~/Library/Caches/com.anthropic.claudefordesktop.ShipIt/ShipItState.plist` shows exactly this (launchAfterInstallation true, target /Applications/Claude.app) and the log shows a completed install and relaunch on 2026-11-21. Installed Claude 6.28899.6, bundle `com.anthropic.claudefordesktop`, ships Squirrel/Mantle/ReactiveObjC frameworks. Codex (`/Applications/ChatGPT.app`, `com.openai.codex`) ships **Sparkle.framework**, not Squirrel.
**Sparkle (Codex/ChatGPT, observed from the framework in the bundle; OpenAI's docs do not name the framework).** Sparkle 2 InstallerProgressAppController.m:329-342: the installer picks only `runningApplications.firstObject` among instances matching the bundle id and path, with a source comment that it does not monitor them all. So which instance blocks the install is arbitrary, and other instances can be left running on a replaced bundle. Not tested by me.
**Windows.** Squirrel.Windows docs (install-process.md): per-user `%LocalAppData%\App`, each version in `app-<version>`, shortcuts go through `Update.exe --processStart`. The page does not say what happens to running processes; my understanding (not verified in a source I read) is that running instances keep their old `app-<old>` folder and the new version starts on the next launch via Update.exe. Electron docs say MSIX is auto-detected and uses its own updater. MSIX update behaviour for running instances: not verified (user reports describe the package being closed for update, claudeissues #46179, unverified).
**Per client:**
- Claude: macOS = Squirrel.Mac (verified locally). Windows = MSIX in current docs (Cowork requires .msix); legacy Squirrel exe installer exists (claude.com installation docs via search; support.claude.com article 12622703: checks about every 4 hours, applies automatically).
- Codex / ChatGPT: macOS = Sparkle (framework present locally). Windows: unknown.
- Cursor: VS Code fork with `update.mode`; underlying macOS mechanism most likely Electron autoUpdater but UNVERIFIED (not installed here, source not read). Windows: unknown (community posts mention `update.enableWindowsBackgroundUpdates`).
- Kimi: unknown. Release notes mention an "in-app update" on Windows; one third-party report (runtimewire, about a different Kimi Desktop component) is not about the updater of Kimi Work. Kimi Work is default-slot only in AgentDesk.

## Part 3 - Why all instances are affected on macOS; Windows
Squirrel.Mac keys everything on the bundle (identifier + URL), not on a user-data-dir: one ShipIt job, one state file, one cache dir, one target `/Applications/X.app`. Any instance that downloads stages the update for the whole bundle. The swap needs every instance of that bundle gone (Squirrel), or at least the first-matched one (Sparkle). Replacing the bundle under a running Electron instance is unsafe (old resources, helper apps, asar), which is why ShipIt refuses with `AppStillRunning`. The relaunch is a single default launch. The owner's observation fits: the instance that clicked "restart" quit, nothing could install until the others also quit, and afterwards one default-account window came back.
Windows (Squirrel.Windows): versions sit side by side, so the swap does not need other instances closed in principle; old instances keep running the old folder, which is why per-instance updates are possible there. MSIX: package replacement generally needs the app closed (unverified; user reports).

## Part 4 - Options
**A. Coordinated update by AgentDesk.** Feasible on macOS without touching client internals: (1) detect "update waiting": ShipIt cache `~/Library/Caches/<bundleId>.ShipIt/` containing `update.*` dir / ShipItState.plist whose `targetBundleURL` matches the installed app; (2) detect version drift: `CFBundleShortVersionString` on disk (already read at main.js:4402) vs process start time older than the bundle's Info.plist mtime (the PID's executable path/start time is available from `ps`); (3) show list: profiles with `status().active` (profile-runtime.js:481); conversation-running info is NOT available today (needs per-client session scanner; mark "unknown" honestly); (4) on confirm, `stopProfile` for each profile of that client, wait until ShipIt exits and plist version changes, then relaunch exactly the recorded set (needs a new persisted "was open" list). This does not make updates independent; it makes the shared restart orderly.
**B. Separate app copy per account.** Verdict: not recommended. Copy under another path keeps Apple signature valid (a plain `cp -R` preserves it; renaming/editing Info.plist or the bundle id breaks sealing and notarisation re-check/Gatekeeper). Keeping the same bundle id: Squirrel's ShipIt state/cache dir and launchd job label are shared per bundle id, so copies collide on state (target URL differs, but one state file); LaunchServices picks an arbitrary copy for the bundle id. Changing the bundle id requires re-signing (ad-hoc), which loses notarisation, breaks Squirrel's check that the update's signature matches the current app (SQRLInstaller prepareAndValidate), and renames the keychain "Safe Storage" item and per-app permissions (not verified here; Chromium names it by app, so a copy with the same name shares it).
**C. Turn off auto-update.** Citable switches only: Cursor / VS Code `"update.mode": "none"` (official VS Code FAQ; Cursor values `default`, `manual`, `none`, `silentlyApplyOnQuit` from Cursor community posts, not official docs; staff say `none` covers only app binary updates); Windows `update.enableWindowsBackgroundUpdates:false` (community). Claude Desktop: `disableAutoUpdates` policy = 1 (support.claude.com 12622703; registry/MDM location only in another article I did not read). ChatGPT/Codex desktop: `in_app_updates = false` under `[features]` in requirements.toml (OpenAI enterprise doc; admin-managed, not a user setting). Kimi: none found. These are client config, so AgentDesk must not write them (AGENTS.md: provider/client config belongs to the client/configurator). AgentDesk could at most explain and link.
**D. CLI clients.** Claude Code docs: updates install in the background and "take effect the next time you start" a session; a running session reads parts of its executable from disk, and in-place replacement (npm install -g deleting the old binary) can crash sessions on shared/network storage; native installer keeps the previous versions on disk locally. So, on a single local machine, running sessions normally continue, but this is documented only for Claude Code. `DISABLE_AUTOUPDATER=1` in settings `env` stops background checks; `claude update` still works; `DISABLE_UPDATES` blocks all. Other CLIs (Codex, Gemini, OpenCode, Cursor Agent, Copilot): not verified.

## Part 5 - Recommendation
Promise "orderly", not "independent". Truthful: AgentDesk can show that an update is staged, which accounts of that client are open, close and reopen exactly those, and warn it will interrupt. Cannot promise: independent per-account restart on macOS (one bundle, one ShipIt); knowing whether a conversation is running (not today); control over what the client relaunches; Cursor/Kimi/Codex mechanics (unverified). On Windows independence is plausible for Squirrel.Windows only. Suggested first step: read-only "update waiting / running old version" indicator plus an explanation in the tools dialog; add the coordinated restart later behind explicit confirmation. Do not do B.
