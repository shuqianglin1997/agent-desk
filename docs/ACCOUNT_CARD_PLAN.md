# 账号名片：把一个账号导出成文件交给别人

> 状态：草案，待所有者审阅。排在 `docs/ARCHITECTURE_PLAN.md` 的九个阶段全部完成之后开发，并按整理后的架构来写。
>
> 本文同时是基准第 3 节第 21 条要求的那次“单独的产品与安全评审”。批准本文意味着给第 21 条加一个有限的例外（见第 6 节），其余不变。
>
> 证据：`docs/feature-evidence/A-credentials.md`（各家客户端的登录状态存在哪、能不能带走、条款原文）。

## 1. 要解决的事

所有者的原话：登记过的账号“可以发送给其他人，就是有一个专门的格式或者文件，导出之后能记录这个账号的信息……其他人拖进我这个工具里，直接就能在卡片那里加上这个 Agent，然后也能就登录那个对应的账号。当然得他电脑上有对应的软件，如果没有的话就提示他去下载。”

## 2. 先说清一个前提

密码和令牌没有登记在 AgentDesk 里。每个账号是一个独立的数据目录，登录状态在官方客户端自己的文件或系统钥匙串里；AgentDesk 只是让客户端用那个目录启动，所以再打开不用重新登录。“导出账号”实际是把官方客户端的登录状态带走，能不能成取决于各家把它存在哪。

## 3. 查证结果：哪些带得走

| 类别 | 例子 | 结论 |
|---|---|---|
| 接口密钥、服务商密钥 | Claude Console 密钥、OpenAI 密钥（`codex login --with-api-key`）、`GEMINI_API_KEY`、Kimi 平台密钥、DSH 的 DeepSeek 密钥、Qwen 的服务商密钥、OpenCode 里的密钥条目 | **带得走**，而且是服务商自己支持的配置方式 |
| 存成文件的订阅登录 | Codex 的 `auth.json`、Kimi Code、Qwen 的 OAuth、Windows 上的 Claude 命令行 | 拷得走，但**两个人不能同时用**：刷新令牌只能用一次，Codex 源码里把重复使用标成 `refresh_token_reused`。两边都用会互相顶下线 |
| 存在系统钥匙串里的登录 | macOS 上的 Claude 命令行、Gemini 命令行、Claude 桌面端、Copilot | **带不走**：密钥绑在本机；Gemini 的文件备份用“主机名加用户名”做盐，换台机器解不开 |
| 没查清 | Cursor、Kimi Work | 按带不走处理，查清再说 |

条款方面：OpenAI、Anthropic、Kimi Code、阿里的 Coding Plan、GitHub 的条款都不允许把账号或登录交给另一个人用；Google 和 Cursor 只写了账号由本人保管。接口密钥通常归付费的那个组织，规则不同。原文和链接在证据里。

## 4. 建议做什么、不做什么

### 4.1 做：两档名片

**第一档：名片（不带登录）。** 所有客户端都能用。

- 内容：名字、客户端与形态、猫的毛色项圈配饰、备注；接口类账号再加不算秘密的配置（服务商标识、接口地址、模型名）。
- 对方拖进来就得到这张卡片和这只猫，状态是“需要登录”，点一下走官方登录，或粘贴自己的密钥。
- 文件是可读的明文 JSON，导出前把将写进去的内容逐项列给人看。

**第二档：带密钥的名片。** 只对第 3 节第一类开放。

- 密钥加密后放进文件，解锁码只显示一次，和文件分开发；做法与“交接任务”相同。
- 对方拖进来、输入解锁码后，AgentDesk 把密钥交给官方客户端自己保存，卡片直接可用。
- 默认 7 天后失效，过期的文件拒绝导入。

### 4.2 不做：把订阅登录发给别人

理由有三条，都来自查证：

- 一半的客户端在技术上就带不走。
- 带得走的那几家，两个人同时用会互相顶下线，结果是“看起来能用，过一会儿两边都掉”。
- 多数服务商的条款明确不允许，账号有被封的可能；一个开源工具内置这个功能，也会让项目本身被当成共享账号的工具。

对这类账号，导出时如实显示“这种登录带不走”，并给出能走的路：发第一档名片让对方自己登录；需要多人用同一个订阅时，用服务商的团队版邀请对方。

所有者自己在另一台电脑上用同一个账号，属于另一回事：在那台电脑上走官方登录即可，不需要本功能。

### 4.3 对方没装客户端

沿用招募里现有的做法：卡片先出现，状态是“缺少客户端”，给出官方下载入口；装好后继续，不重复建卡。

## 5. 流程

**导出**（猫的档案里“导出名片…”）

1. 选哪一档。账号的登录属于带不走的类别时，第二档不可选并写明原因。
2. 预览将写入的内容，一项一项列出，密钥本身不显示。
3. 用系统的保存框存成 `.agentdesk-account`。
4. 第二档：显示一次解锁码，并提示“这个文件加解锁码等于这把密钥；不再需要时去服务商后台作废密钥”。

**导入**（把文件拖到名册上，或在招募里选“名片”）

1. 先校验再做任何事：格式、版本、类别、客户端是否认识、是否过期、大小上限。
2. 预览：名字、客户端、带不带密钥。**接口地址单独醒目显示并要求确认**，因为一张恶意名片可以把客户端指向别人的服务器来截取代码和对话。
3. 第二档：输入解锁码。错误或文件被改过，统一报“解不开”。
4. 没装客户端时走 4.3。
5. 建独立的数据目录，交接密钥，卡片出现。任何一步失败都不留下半张卡。

## 6. 安全要求（评审结论）

- 解密后的密钥只在主进程的内存里，直接交给官方客户端；不进界面、日志、命令行参数、历史记录，用完清除。
- 导出时主进程可以从“本工具的适配器自己写过、且服务商文档写明的那个文件”里把密钥读回来，只为放进加密容器。钥匙串里的、别的来源的一律不读。这是对 `AGENTS.md` 里密钥那一段的一处补充，需要所有者同意。
- 名片里只接受白名单字段。不接受可执行文件路径、任意环境变量、任意配置正文、脚本。
- 名字和备注是数据，照常转义；不能当指令。
- 名片不进 Mesh、不建立信任、不同步。导入得到的是一只新猫，有自己的标识，不与发送方的账号合并。
- 加密容器与任务包用同一份实现，但类别不同，任务包永远不能携带登录，名片永远不能携带会话。
- 不能承诺的要写明：文件可以被复制，所以“只能导入一次”做不到；真正的撤销只有在服务商后台作废密钥。

对基准第 21 条的修改（批准后写入）：在“密码、Token、Cookie 和官方浏览器登录数据继续不跨设备”之后加一句例外——“用户显式导出的、服务商支持以配置方式提供的接口密钥，可以放进加密的账号名片交给另一台设备或另一个人”。

## 7. 落在整理后的架构里

| 放在哪一层 | 内容 |
|---|---|
| `clients/<id>` | 每家适配器声明自己有哪几种登录方式，各自“带得走 / 会互相顶 / 带不走”；提供“给出不含秘密的配置”“读回可携带的密钥”“交接密钥”（最后一项已有）。界面和命令只问适配器，不写按客户端名字的判断 |
| `core` | 加密容器从任务包里提出来成为公共件，带类别；名片与任务包共用 |
| `services` | 名片的组装、解析和校验，纯函数，不碰界面 |
| `commands` | `account.card.export`、`account.card.inspect`、`account.card.import`，各有“现在能不能做”和固定的原因码（如 `login-not-portable`、`client-missing`、`card-expired`、`unlock-failed`）。界面和命令行共用；命令行的解锁码只从标准输入读 |
| 存盘 | 导出导入的历史用统一的存盘件，带版本；只记编号、时间、类别、客户端 |
| `ui` | 一个对话框，用公共的对话框外壳；拖入复用招募的拖放处理 |

验收里固定包含：分层检查通过；适配器之外没有新增的按客户端名字的判断；三语词表一致；`ARCHITECTURE_PLAN.md` 第 8 节的各项指标不倒退。

## 8. 分批

1. 公共加密容器、名片格式、各适配器的登录方式声明（没有界面）。测试覆盖：往返、被改、过期、越界字段、假密钥不出现在任何输出里。
2. 三条命令和命令行入口。
3. 界面：档案里的导出、拖入导入、预览与接口地址确认、缺客户端的路径。
4. 文档、不显示窗口的界面走查。真实账号的往返要所有者在两台电脑上实测。

## 9. 顺带发现，交给架构整理的第 3 阶段

现有的 Gemini 拖入导入写的是明文的 `oauth_creds.json`，而现在的 Gemini 命令行会把它迁进钥匙串或绑定本机的加密文件，实际行为和代码假设的不一样，需要复核。

## 10. 要所有者定的

1. 范围：只做 4.1 的两档，不做订阅登录的转交（建议如此）。
2. 导出第二档时，是让主进程从客户端文件里读回密钥（建议），还是每次要人重新粘贴一遍。
3. 带密钥的名片默认多久失效（建议 7 天）。
4. 名字用“账号名片”是否合适。
