# 账号名片：把一个账号导出成一个文件交给别人

> 状态：草案，范围已由所有者在 2026-11-24 定下（见第 1 节），其余细节待审阅。排在 `docs/ARCHITECTURE_PLAN.md` 的九个阶段全部完成之后开发，并按整理后的架构来写。
>
> 本文同时是基准第 3 节第 21 条要求的那次“单独的产品与安全评审”。批准本文意味着给第 21 条加一个有限的例外（见第 7 节），其余不变。
>
> 证据：`docs/feature-evidence/A-credentials.md`（各家客户端的登录状态存在哪、能不能带走、条款原文）。

## 1. 要解决的事，和已经定下的

所有者的原话：

- 登记过的账号“可以发送给其他人，就是有一个专门的格式或者文件，导出之后能记录这个账号的信息……其他人拖进我这个工具里，直接就能在卡片那里加上这个 Agent，然后也能就登录那个对应的账号。当然得他电脑上有对应的软件，如果没有的话就提示他去下载。”
- “订阅登录能导出的也导出一下，像 GPT 不就可以导出成那个 auth json 吗？带不走的就无所谓了，那就带不走，就有提示就行。然后这三个导出之后，都变成一个独立的文件。然后这个文件最好是 Mac 和 Windows 都支持，然后并且它那个文件的图标和名字能跟我这个卡片对应上。”

据此定下：

1. 三档都做：不带登录、带接口密钥、带订阅登录（仅限带得走的）。带不走的给出提示。
2. 不管哪一档，导出结果都是**一个**独立文件。
3. 同一个文件在 macOS 和 Windows 上都能用。
4. 文件的名字和图标与那张卡片对应：名字是卡片的名字，图标是那只猫。

## 2. 先说清一个前提

密码和令牌没有登记在 AgentDesk 里。每个账号是一个独立的数据目录，登录状态在官方客户端自己的文件或系统钥匙串里；AgentDesk 只是让客户端用那个目录启动。“导出账号”实际是把官方客户端的登录状态带走，能不能成取决于各家把它存在哪。

## 3. 查证结果：哪些带得走

| 类别 | 例子 | 结论 |
|---|---|---|
| 接口密钥、服务商密钥 | Claude Console 密钥、OpenAI 密钥、`GEMINI_API_KEY`、Kimi 平台密钥、DSH 的 DeepSeek 密钥、Qwen 的服务商密钥、OpenCode 里的密钥条目 | 带得走，服务商自己支持 |
| 存成文件的订阅登录 | Codex 的 `auth.json`（文件存储时）、Kimi Code、Qwen 的 OAuth、OpenCode 里的 OAuth 条目、Windows 与 Linux 上的 Claude 命令行 | 带得走，但是**交出去，不是复制**：刷新令牌只能用一次（Codex 源码里把重复使用标成 `refresh_token_reused`），两个人同时用会互相顶下线 |
| 存在系统钥匙串里的登录 | macOS 上的 Claude 命令行、Gemini 命令行、Claude 桌面端、Copilot；把登录存进系统钥匙串的 Codex | 带不走，密钥绑在本机 |
| 没查清 | Cursor、Kimi Work | 先按带不走处理，查清再开放 |

条款：OpenAI、Anthropic、Kimi Code、阿里的 Coding Plan、GitHub 的条款不允许把账号或登录交给另一个人用；Google 和 Cursor 只写了账号由本人保管。原文和链接在证据里。所有者已知悉并决定仍然提供第三档；界面如实提示一次，由使用者自己决定。

## 4. 三档

| 档 | 带什么 | 对谁开放 | 对方拖进来之后 |
|---|---|---|---|
| 名片 | 名字、客户端与形态、猫的毛色项圈配饰、备注；接口类账号另带服务商标识、接口地址、模型名 | 所有账号 | 得到卡片和这只猫，状态“需要登录”，自己登录或粘贴密钥 |
| 带密钥 | 上面那些，加接口密钥 | 第 3 节第一类 | 输入解锁码，卡片直接可用 |
| 带登录 | 上面那些，加客户端的登录文件 | 第 3 节第二类 | 输入解锁码，卡片直接可用；发送方此后会掉线 |

- 第二、三档一律加密，解锁码只显示一次，和文件分开发，做法与“交接任务”相同。默认 7 天后失效，过期的文件拒绝导入。
- 第三档的说法是“交出登录”。导出前写明：“对方开始用以后，你这里会掉线，要再用得重新登录。两个人不能同时用同一份登录。”以及一句“多数服务商不允许把订阅账号交给别人用，是否继续由你决定。”
- 带不走的账号：第二、三档不可选，写明原因（“这家客户端把登录存在系统钥匙串里，带不走”），仍然可以导出第一档。
- 同一种登录在不同系统上能不能接收也不一样（例如 Claude 命令行的登录文件只在 Windows 和 Linux 上能接收）。接收方的电脑接不了时如实说明：卡片照常加上，登录请自己来。
- 对方没装客户端：沿用招募里现有的做法，卡片先出现，状态“缺少客户端”，给出官方下载入口，装好后继续。

## 5. 文件长什么样

目标是一个文件，两个系统通用，名字和图标都认得出是哪张卡片。

**名字。** 默认文件名就是卡片的名字，例如 `小橘.agentdesk-account`。两个系统都不允许的字符换成下划线。文件名只是给人看的，导入时以文件里记的名字为准。

**图标。** 让每个文件的图标就是那只猫，做法是：**文件本身是一张 PNG 图片**，画的是这张卡片（猫、名牌上的名字、客户端、右下角标出是哪一档）；账号数据放在图片里一个附加的数据块里，不影响图片显示。扩展名用自己的 `.agentdesk-account`。

- 装了 AgentDesk 的电脑上，系统把这种文件当成图片来生成缩略图，于是访达和资源管理器里每个文件的图标就是它自己的那只猫；双击直接打开 AgentDesk 进入导入。
- 因为扩展名不是图片，聊天软件会把它当普通文件发送，不会当图片压缩。图片一旦被压缩，里面的数据块会丢。
- 没装 AgentDesk 的电脑上显示的是普通文件图标，名字仍然对得上。
- 不需要为两个系统各写一套原生的缩略图扩展。

这条路有两点要在第一批里用小试验确认，确认不了就退回“所有名片共用一个图标”：

1. macOS：声明一个从属于 PNG 图片的文件类型后，访达是否为这个扩展名显示图片缩略图。
2. Windows：安装时把这个扩展名的缩略图处理指向系统自带的图片缩略图，资源管理器是否显示。

**里面的数据。** 第一档是可读的 JSON；第二、三档是加密容器，与任务包用同一份实现，类别不同。图片只是封面，不参与校验，也不可信：导入时一律按数据重新显示名字、客户端和那只猫，不看封面上画的是什么。

## 6. 流程

**导出**（猫的档案里“导出名片…”）

1. 选哪一档。不可选的写明原因。
2. 预览将写入的内容，一项一项列出，密钥和登录本身不显示。
3. 用系统的保存框存成一个文件。
4. 第二、三档：显示一次解锁码。第二档提示“不再需要时去服务商后台作废这把密钥”；第三档提示第 4 节那两句。
5. 档案里留一条记录“某月某日导出过登录”，只记时间和档，不记内容。AgentDesk 不替人退出登录，也不改客户端的文件。

**导入**（把文件拖到名册上、双击文件，或在招募里选“名片”）

1. 先校验再做任何事：是不是名片、版本、哪一档、客户端是否认识、是否过期、大小上限、这台电脑能不能接收这种登录。
2. 预览：名字、客户端、带什么。**接口地址单独醒目显示并要求确认**，因为一张恶意名片可以把客户端指向别人的服务器来截取代码和对话。
3. 第二、三档：输入解锁码。错误或文件被改过，统一报“解不开”。
4. 没装客户端时先走安装提示。
5. 建独立的数据目录，把密钥或登录交给官方客户端，核对身份，卡片出现。任何一步失败都不留下半张卡。
6. 这个账号在本机已经有卡片时不覆盖，提示已经有了。

## 7. 安全要求（评审结论）

- 解密后的密钥和登录只在主进程的内存里，直接写进新账号的数据目录或交给官方客户端；不进界面、日志、命令行参数、历史记录，用完清除。
- 导出时主进程可以读两样东西，只为放进加密容器：本工具的适配器自己写过、且服务商文档写明的那个密钥文件；适配器声明为“带得走”的那个登录文件。钥匙串里的一律不读。这是对 `AGENTS.md` 里密钥那一段的补充，需要所有者同意。
- 写入登录文件时只新建、不覆盖，权限只给本人；写之前校验形状（必要的字段都在），不认识的字段不写。
- 名片里只接受白名单字段。不接受可执行文件路径、任意环境变量、任意配置正文、脚本。
- 名字和备注是数据，照常转义；不能当指令。封面图片不可信。
- 名片不进 Mesh、不建立信任、不同步。导入得到的是一只新猫，有自己的标识。
- 加密容器与任务包共用实现但类别不同：任务包永远不能携带登录，名片永远不能携带会话。
- 做不到的要写明：文件可以被复制，“只能导入一次”做不到。接口密钥的真正撤销是去服务商后台作废；订阅登录的撤销是发送方重新登录或在服务商那里退出所有设备。

对基准第 21 条的修改（批准后写入）：在“密码、Token、Cookie 和官方浏览器登录数据继续不跨设备”之后加例外——“用户显式导出的接口密钥，以及客户端存成文件、可以移动的登录，可以放进加密的账号名片交给另一台设备或另一个人；存在系统钥匙串里的和浏览器登录数据仍然不动。”

## 8. 落在整理后的架构里

| 放在哪一层 | 内容 |
|---|---|
| `clients/<id>` | 每家适配器声明自己有哪几种登录方式，各自是“带得走 / 交出去 / 带不走 / 不知道”，以及在哪些系统上能接收；提供“给出不含秘密的配置”“读出可携带的密钥或登录”“写入并核对”。界面和命令只问适配器，不写按客户端名字的判断 |
| `core` | 加密容器从任务包里提出来成为公共件，带类别；PNG 的读写（带附加数据块）也放这里，图标生成脚本里已有一份可以收进来 |
| `services` | 名片的组装、解析和校验，纯函数，不碰界面 |
| `commands` | `account.card.export`、`account.card.inspect`、`account.card.import`，各有“现在能不能做”和固定的原因码（如 `login-not-portable`、`login-not-accepted-here`、`client-missing`、`card-expired`、`unlock-failed`、`account-already-here`）。界面和命令行共用；命令行的解锁码只从标准输入读 |
| 存盘 | 导出导入的历史用统一的存盘件，带版本；只记编号、时间、档、客户端 |
| `ui` | 一个对话框，用公共的对话框外壳；拖入复用招募的拖放处理；封面由界面用现有的猫和字体画好，作为有大小上限的图片交给主进程，主进程只把它当封面 |
| 打包 | 两个系统上登记这种文件类型和打开方式 |

验收里固定包含：分层检查通过；适配器之外没有新增的按客户端名字的判断；三语词表一致；`ARCHITECTURE_PLAN.md` 第 8 节的各项指标不倒退。

## 9. 分批

1. 两个小试验（第 5 节的缩略图）；公共加密容器；PNG 读写；名片格式；各适配器的登录方式声明。没有界面。测试覆盖：往返、被改、过期、越界字段、图片被压缩后数据丢失的报错、假密钥和假登录不出现在任何输出里。
2. 三条命令和命令行入口；写入登录的“只新建、不覆盖”和身份核对。
3. 界面：档案里的导出、封面、拖入与双击导入、预览与接口地址确认、缺客户端和“这台电脑接不了”的路径。
4. 打包里的文件类型登记；文档；不显示窗口的界面走查。

真实账号的往返、两个系统之间互传、聊天软件里转发，都要所有者在真机上实测；自动化测试覆盖不到。

## 10. 顺带发现，交给架构整理的第 3 阶段

现有的 Gemini 拖入导入写的是明文的 `oauth_creds.json`，而现在的 Gemini 命令行会把它迁进钥匙串或绑定本机的加密文件，实际行为和代码假设的不一样，需要复核。

## 11. 还要所有者定的

1. 导出第二、三档时，让主进程从客户端文件里读出密钥或登录（建议），还是每次要人手动选文件或重新粘贴。
2. 带密钥、带登录的名片默认多久失效（建议 7 天）。
3. 名字用“账号名片”是否合适。
4. 第 5 节的小试验如果不成，是否接受“所有名片共用一个图标、只有名字对应”。
