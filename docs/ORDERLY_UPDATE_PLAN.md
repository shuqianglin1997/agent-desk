# 客户端更新：做不到互不影响，但可以有序

> 状态：**所有者 2026-11-24 同意，按第 7 节的建议开发**（原话：“按建议做”）。四批已开发完（第 8 节），只在 macOS 上提供。真实的一次更新要所有者在真机上遇到才能验证。
>
> 证据：`docs/feature-evidence/B-updates.md`（读了更新器 Squirrel.Mac 的源码和各家文档；没核实的部分在里面标明）。

## 1. 所有者看到的现象

开着三个同一客户端的账号，其中一个点了更新要重启，另外两个好像也必须关掉才行。希望以后能各自独立。

## 2. 原因

三个账号用的是电脑上装的**同一份**应用，只是各带各的数据目录启动。更新要替换的是那一份应用本身。

- Claude 这类应用在 macOS 上的更新器（Squirrel.Mac）按“这一份应用”排队：下载好以后，要等这份应用所有开着的实例都退出才替换。
- 点“重启更新”只关掉点的那一个；它会一直关着，直到另外两个也退出。
- 换好之后更新器自己重新打开应用时不带数据目录，所以回来的是默认账号，不是原来开着的那几个。

没核实的：Codex 用的是另一种更新器（Sparkle），资料显示它只等第一个匹配的实例，没有实测；Cursor 和 Kimi 用什么没有查到；Windows 上运行中的旧版本会怎样，资料没有说清。

## 3. 能承诺什么

在 macOS 上承诺不了“互不影响”，能承诺的是“有序”：提前知道、一次关齐、换好以后原样重开。

评估过并放弃的两条路：

| 做法 | 为什么不做 |
|---|---|
| 每个账号装一份独立的应用 | 几份副本仍共用同一份更新状态；要彻底分开得改应用标识并重新签名，会丢掉苹果的公证；钥匙串里的加密钥匙也是按应用名共用的 |
| 由 AgentDesk 关掉客户端的自动更新 | 只有 Cursor 有按账号生效的开关，Codex 和 Claude 只有管理员策略，Kimi 没找到；而且这是客户端自己的配置，AgentDesk 不替它写 |

## 4. 要做的

AgentDesk 仍然不下载、不安装任何更新，也不改客户端的更新设置；更新本身始终由官方更新器完成。

1. **记下来。** 每次打开一个账号时，记下它启动时应用的版本；并一直记着“现在开着哪几个”。
2. **看得见。** 磁盘上应用的版本比某个开着的账号启动时的版本新，或发现更新器已经备好新版本时，在这个客户端的卡片上给一个小记号“有更新在等”。前一种是确切的，后一种是推断的，如实标注；判断不了就不显示。不响声音，不弹窗。
3. **一起重开。** 记号上的动作：
   - 先列出会被打断的账号，标出哪几个有对话在跑、哪几个有调度中枢的后台对话。有后台对话在跑时默认不让继续，要人明确选择。
   - 确认后，用现有的关闭动作把这个客户端的账号逐个关掉，等它们都退出，等新版本换好，再把刚才开着的那几个各带各的数据目录重新打开。
   - 等不到新版本换好时如实说明并停在那里，不强行继续。
4. **补救。** 人直接在客户端里点了更新也没关系：AgentDesk 发现这个客户端的账号都退出了、版本变了，就提供一个“把刚才开着的 3 个重新打开”。这正对应所有者遇到的情况。
5. **命令行工具。** 在“工具”里更新命令行客户端之前，如果它有对话在跑，先提示“有 N 条在跑，更新可能打断”。已核实的只有 Claude Code（下次启动才生效）；用 npm 原地替换时运行中的会话可能出错，其他工具没核实，所以一律先提示。

不做的：自动更新、定时更新、替人决定什么时候重启。更新器自己重新打开的那个默认实例不是 AgentDesk 启动的，AgentDesk 不去关它。

## 5. 落在整理后的架构里

| 放在哪一层 | 内容 |
|---|---|
| `clients/<id>` | 每家适配器声明自己的更新方式（Squirrel、Sparkle、MSIX、VS Code 系、不知道）和“怎么看出有更新在等”。不知道就声明不知道 |
| `core` | “有更新在等”用统一的事实类型表达：确切、推断、不知道 |
| `services` | 运行时服务记录启动版本和开着的集合，放进统一的存盘件并带版本迁移；关闭、等待、重开的顺序由它负责，进程的归属沿用现有规则，只动 AgentDesk 自己启动的 |
| `commands` | `client.update.status`、`client.update.restartAll`、`client.reopenSet`，带“现在能不能做”和固定原因码；只读的状态查询界面和命令行共用；关闭与重开只在窗口里由人触发 |
| `ui` | 卡片上的记号、确认对话框，用公共部件 |

验收里固定包含：分层检查通过；适配器之外没有新增的按客户端名字的判断；三语词表一致；`ARCHITECTURE_PLAN.md` 第 8 节的各项指标不倒退。

## 6. 分批

1. 记录启动版本和开着的集合；判断“有更新在等”；只有数据，没有界面。
2. 三条命令和关、等、开的顺序。测试用假的进程和假的版本号，不碰真的应用。
3. 卡片记号、确认对话框、补救入口。
4. 文档、不显示窗口的界面走查。

真实的更新只能由所有者在真机上遇到一次来验证，自动化测试覆盖不到；Windows 要在真机上查清行为之后才开放，在那之前只在 macOS 上提供。

## 7. 所有者已定的（2026-11-24，“按建议做”）

1. 接受“有序”，不追求“互不影响”。
2. 卡片上一个小记号，“工具”里给详情。
3. 人自己在客户端里点了更新之后，主动给出“原样重开”。

## 8. 做成了什么（2026-11-24）

四批各提交一次：`c83784c` 数据，`5648743` 命令与顺序，`43ecbc1` 界面，最后一批是文档。

**记下来。** `profile-runtime.json` 升到第 2 版：每次由 AgentDesk 打开一个账号，就记下启动前从应用包 `Info.plist` 读到的版本和应用包位置。每个客户端另记一个“开着的集合”：从 AgentDesk 打开它的第一个账号算起，凡是这段时间里由 AgentDesk 打开过的账号都在里面，每个账号退出时记下退出时间（再打开就清掉）；AgentDesk 打开的最后一个也退出时，集合结束，并记下最后那次退出的原因。第 1 版的文件照常读，这几项算不知道。

**看得见。** 判断在 `src/client-updates.js`，结果用统一的事实类型：

- 确切：磁盘上的版本比某个开着的账号启动时的版本新；
- 推断：只有 Claude 能看出来——Squirrel 的 `ShipItState.plist` 指向装着的这份应用，它下载好的新应用包还在 ShipIt 的缓存里，而且版本比装着的新（装完以后这份下载的应用包就不在了）；
- Codex、Cursor、Kimi 看不出下载好的更新，只能等到磁盘上的版本变了才是“确切”；其余情况都是不知道，不显示。

卡片上用现有的右上角记号（刷新图标），提示里写明确切还是推断、详情在“系统 › 工具”；“要用户处理”的记号和迷糊的问号仍然优先。“工具”里这个桌面应用的那一行写“有更新在等”，下面一行是开着几个账号、磁盘上已是新版本（或“新版本已下载（推断）”；版本号这一行上面已经有），右边一个“一起重开…”。确认框和收件箱列账号时用卡片上的名字，同一个账号有两个位置时再带上位置自己的名字。

**一起重开。** 确认对话框用公共的对话框部件，逐个列出会被打断的账号，标出谁有对话在跑、谁有调度中枢的后台对话；有后台对话时“关掉并重开”是灰的，要人先勾“同时停下这 N 段后台对话”。确认后的顺序：按人的选择停下后台对话，用现有的关闭动作逐个关掉（原因记为 `client-update`），推断的情况再等新版本换好（最多 3 分钟，每 2 秒看一次），然后把刚才关掉的这些账号各带各的数据目录重新打开。有一个关不掉就停在那里，后面不再关、也不重新打开；等不到新版本时如实说明（可能还有别的窗口开着这个应用），不重新打开。

**补救。** AgentDesk 打开的这个客户端的账号都退出了、磁盘上的版本比它们启动时的新、而且集合不是因为退出 AgentDesk（或移除、移动位置、磁盘事故）结束的，就在收件箱里给一条“{客户端} 已换成 {版本}”，“工具”那一行给“重新打开…”。确认框里每个账号一个勾选框：在最后一个账号退出前 10 分钟内退出的默认勾上；更早退出的默认不勾，旁边写“较早前已关”（退出时间不知道的按勾上算）。人可以改勾选，只打开勾着的；全都不勾时“重新打开”按钮是灰的，Main 也拒绝（`nothing-selected`）。只要再打开这个客户端的任何一个账号，这条就不再出现。“一起重开”不用勾选，它只重开自己刚关掉的那几个。

**命令行工具。** 在“工具”里自动更新一个命令行工具之前，它的账号有对话在跑（活动探测按数据根各数一次，或调度中枢的后台对话，取较大的）就先问一句“有 N 条在跑，更新可能打断”。Codex 的命令行和 Codex 账号共用会话目录，也算在内。

**命令。** 命令表只允许一个点，所以计划里的三条落成 `client.updateStatus`、`client.updateRestartAll`、`client.reopenSet`（通道同名，preload 是 `getClientUpdateStatus`、`restartClientForUpdate`、`reopenClientSet`）。窗口只送客户端标识和“是否停下后台对话”。后两条在命令表里标为只限窗口（`windowOnly`），由人在窗口里点。成品命令行只转发只读的 `clients update-status`（没有桌面在监管时回 `desktop-not-running`）；`clients restart-all`、`clients reopen` 在命令行进程里直接回 `window-only`，不碰桌面。固定原因码：`platform-unsupported`、`client-unknown`、`client-update-busy`、`nothing-open`、`no-update-waiting`、`background-runs-active`、`nothing-to-reopen`、`nothing-selected`，做到一半停下的是 `background-run-stop-failed`、`client-close-failed`、`update-not-installed`、`client-reopen-failed`。

**开发时自己定的、计划没写细的**（所有者可以改）：

1. 补救的确认框列出整段集合，但只默认勾上在最后一个账号退出前 10 分钟内退出的；更早退出的标“较早前已关”、默认不勾，人自己决定开不开（规划会话 2026-11-24 定：一小时前故意关掉的账号不该被“原样重开”打开）。
2. 补救的提示一直留着，直到再打开这个客户端的某个账号；没有单独的“不用了”。
3. 等新版本最多 3 分钟。
4. 命令行只读（规划会话 2026-11-24 定）：只有状态查询；关闭与重开只在窗口里由人触发，命令行回 `window-only`。理由：第 4 节“不替人决定什么时候重启”，命令行是给 AI 用的，开放以后任何 Agent 都能关掉人正开着的客户端，连它自己所在的那个也包括在内。

**没验证的。** 真实的一次更新（Squirrel 真的在这几个实例都退出后换上新版本、重新打开的确是原来那几个）只能由所有者在真机上遇到一次来确认；Codex 的 Sparkle、Cursor 和 Kimi 的更新方式仍按第 2 节没有核实；Windows 不提供。
