01 · 先把工作状态说对

用户管理的是自己的 Agent，
设备只是它们可以工作的端口。

一个账号能同时登录多台电脑，一台电脑也能登录多个账号。主界面必须先展示去重后的全局 Agent，再用设备筛选和运行位置选择器决定动作落到哪里。

一只猫 = 一个全局 Agent。
不是一台机器，也不是一个客户端文件夹。

MacBook 今天是控制台，Mac Studio 和 Windows 工作站是执行端；明天角色可以互换。设备加入不会复制猫，设备删除也不会误删其他设备上的同一 Agent。

真正的动作目标：deviceId + profileId。
真正的展示身份：agentId。

03 · 正确身份模型

项目、会话、压缩、分支、设备副本，必须各有自己的生命。

只要这六层不混，压缩、归档、跨设备复制和内部 Agent 执行都不会制造假项目。列表只认 ConversationIdentity；其他对象要么是归属，要么是内部状态，要么是动作位置。

默认显示ConversationIdentity；列表的一行就是用户的一条对话。
默认隐藏Checkpoint 与 ExecutionBranch；它们只能在诊断谱系中展开。
动作前选择SessionReplica；复制、打开、发送都落到确切设备位置。

六层技术对象：ProjectIdentity / ConversationIdentity / ConversationCheckpoint / ExecutionBranch / SessionReplica / PhysicalSessionRecord。

05 · 前后端与 P2P 数据路径

任意设备都能当控制台，信令只负责会合，业务数据留在设备之间。

身份修正必须先在每台来源设备的适配器完成，再发布归一化库存。否则错误的 16 行会被同步到每台电脑，重复问题会被 Mesh 放大。

来源先分类每台设备先把 root / checkpoint / branch 分清，再同步 ConversationIdentity。
服务端不授权设备证书与本机策略决定能力；信令不能冒充设备。
动作是语义 ID远端只收 profileId、conversationId 等稳定 ID，不收任意命令或路径。
一个输入目标可同时观察多台设备，但键鼠只发往明确高亮的一台。
06 · 开发顺序由依赖决定

先修身份，再同步；先能找到会话，再远控。

如果先接 P2P，当前的错误索引会被复制到所有设备。正确顺序是先把本地事实变干净，再建立目录和库存，最后才增加文件、屏幕和输入能力。

Codex 适配器：从物理记录到列表行的分类流程 
for each physical record:
  meta = readSessionMeta(record)
  physicalRecordId = meta.payload.id

  if meta.parent_thread_id
     or meta.thread_source == "subagent"
     or meta.source.subagent exists:
       kind = INTERNAL_CHILD
       parentKey = meta.parent_thread_id or meta.session_id
       attachToDiagnosticLineage(parentKey)
       neverCreateVisibleRow()
  else:
       kind = USER_ROOT
       adapterConversationKey = meta.session_id or meta.id
       upsertOneConversation(adapterConversationKey)
       parseCompactedEventsAsCheckpoints()

  resolveProjectSeparately(cwdAsBindingHintOnly)

归档规则：会话状态只看用户根。父根在 archived、guardian 在 active 时仍是已归档；父根缺失时 guardian 进入 diagnostic-orphan，不晋升为用户会话。
